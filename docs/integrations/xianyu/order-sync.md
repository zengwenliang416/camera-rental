# 闲管家订单同步

## 当前接口快照

已于 `2026-07-23` 根据官方在线 Markdown 核对：

| 接口 | 方法与路径 | 首期用途 |
| --- | --- | --- |
| 订单列表 | `POST /api/open/order/list` | 按时间窗口增量补偿 |
| 订单详情 | `POST /api/open/order/detail` | 按 `order_no` 补全和复核 |
| 订单推送 | 商家配置的 `POST` 回调地址 | 触发详情补拉 |

订单卡密、物流发货和修改价格不在首期只读范围。

## 同步策略

采用“订单推送 + 定时增量同步 + 订单详情补拉”：

1. 保存未经业务处理的原始推送。
2. 使用 `channel + application_id + external_order_no` 幂等。
3. 查询订单详情并保存原始响应。
4. 转换为内部租赁订单。
5. 解析 `seller_remark` 中的租期。
6. 触发排期计算或进入人工复核。
7. 使用安全游标补偿推送遗漏和状态变化。

## 分页边界

- 订单列表 `update_time` 只允许查询最近六个月内的时间范围。
- `page_no` 范围为 `1..100`，`page_size` 范围为 `1..100`，同一查询条件
  翻页超过一万条会报错。
- 每次运行固定 `update_time` 上界，并把大窗口递归拆成不会触及一万条上限的
  小窗口。
- 保存最后更新时间和稳定的并列订单号游标；处理相同更新时间的多条记录。
- 记录服务端数量、接收数量、去重数量和失败数量。
- 在开始翻页前后比较窗口边界，不能用“当前时间不断前移”的查询。
- 失败时从安全游标恢复，不从不确定位置继续。
- 同一租户的店铺授权同步和订单同步分别使用资源级分布式锁；同类任务互斥，
  但耗时订单同步不会阻塞授权状态刷新。

订单列表请求可包含：

```text
authorize_id
order_status
refund_status
order_time (已废弃)
pay_time
consign_time
confirm_time
refund_time
update_time: [startEpochSeconds, endEpochSeconds]
page_no
page_size
```

同步默认使用 `authorize_id + update_time + page_no + page_size`。状态筛选只用于
专项重放，不作为常规增量游标，避免漏掉状态变化。

订单详情请求：

```json
{"order_no":"<external-order-no>"}
```

## 关键字段

| 外部字段 | 内部用途 | 规则 |
| --- | --- | --- |
| `order_no` | 外部订单号 | 作为幂等键的一部分 |
| `authorize_id` | 店铺授权 | 同步前校验授权 |
| `seller_remark` | 日期解析原文 | 原文必须保留 |
| `total_amount` | 下单金额 | 官方明确单位为分，不覆盖实付金额 |
| `pay_amount` | 总租金收入 | 官方明确单位为分，直接按整数分保存 |
| `refund_amount` | 退款统计 | 订单列表明确单位为分；与租金、押金、赔偿分开 |
| `express_fee` | 运费 | 官方明确单位为分 |
| `goods.price` | 商品单价 | 官方明确单位为分 |
| `update_time` | 增量时间 | Unix 秒；与 `order_no` 组成稳定并列游标 |
| `consign_type` | 发货类型 | `1` 物流发货，`2` 虚拟发货；内部不得据此猜测租赁交付完成 |

订单列表响应包含 `list`、`count`、`page_no` 和 `page_size`。详情和列表都可能
携带收件人、手机号和地址；这些字段只进入受控原始 / 标准化存储，不进入普通
日志或默认列表响应。

本地会严格校验分页字段为整数、页码/页大小边界、请求与响应页元数据一致，并
根据 `count/page_no/page_size` 校验当前页应返回的精确条数。手工窗口开始时间
早于当前 `Asia/Shanghai` 时间六个月时会在发起远程请求前拒绝。

增量窗口存在重叠时，若本地订单已有详情载荷且 `source_updated_at` 不早于列表
返回的 `update_time`，该订单计为去重成功并跳过重复详情请求；发生变化的订单
仍按官方流程逐单补拉详情。

后台遗留详情补偿只选择 `detail_json` 缺失且具备非空 `external_order_id` 的订单，
并按 `source_updated_at`、本地 `id` 倒序优先补最新更新的订单。服务层会再次跳过
空白外部订单号，避免用空 `order_no` 调用订单详情接口，并继续处理同批次其他
有效订单。该补偿路径不推进订单分页 cursor。

订单列表页响应会以 `ORDER_PAGE` 写入受限原始载荷表。管理员使用单独的
`rental:xianyu:replay` 权限重放 `ORDER_PAGE` 时，只从本地持久化页解析订单号和
更新时间，按同一“本地详情是否已是最新”的规则补拉缺失或过期详情；该重放不会
推进订单分页 cursor，也不会执行任何第三方写操作。详情响应仍以 `ORDER_DETAIL`
保存，详情 raw payload 重放只重建本地订单详情，同样不推进 cursor。

`pay_amount` 的在线 OpenAPI 类型为 `int64`。内部订单表必须使用 `BIGINT` 分值列，
不能以 32 位 `INT` 截断大额订单。

## 状态基线

当前订单状态：

```text
11 待付款
12 待发货
21 已发货
22 已完成
23 已退款
24 已关闭
```

当前退款状态：

```text
0 未申请退款
1 待商家处理
2 待买家退货
3 待商家收货
4 退款关闭
5 退款成功
6 已拒绝退款
8 待确认退货地址
```

外部状态只映射到渠道订单状态，不直接覆盖内部租赁订单状态机。

## 备注解析

- 明确 `#租期7.25-7.27#` 时优先使用明确租期。
- 只有收货和发回时，收货次日开始计租，发回当天计租。
- 发货日期不参与计租天数。
- 缺少年份时结合订单时间推断。
- 日期冲突或字段不足时进入人工复核。
- 原始备注、解析版本、结果和错误原因一起保存。

## 测试

- 分页和安全游标。
- 外部订单幂等。
- 多店铺隔离。
- 详情补拉失败重试。
- `ORDER_PAGE` 重放不推进 cursor，且保留成功 / 失败计数。
- 六个月边界和一万条窗口拆分。
- 相同 `update_time` 下多个订单不丢失。
- 备注解析失败仍计入总租金。
- 分币、跨月和跨年分摊总额守恒。
