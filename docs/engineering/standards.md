# 工程规范：复用、分层与设计模式

入口为 [根 AGENTS](../../AGENTS.md)。新增能力、重构或审查时只读相关章节；
以下是新改动应遵循的约束，不表示所有历史代码已符合，也不授权顺带重构存量实现。

## 1. 先发现，再复用

实施前沿目标业务入口查看调用链，至少检查：同类实现、已有公共能力、实际调用方、
相关测试。可用 CodeGraph 时先定位；仅按类名或文件名相似不能证明语义相同。

按以下顺序选择：

1. 直接使用已有领域服务、API、组件、hook/composable、工具或依赖。
2. 通过组合现有能力完成新用例，保留原有职责。
3. 在原抽象职责内扩展明确的参数或行为，验证所有受影响消费者。
4. 重复逻辑具有相同业务语义、共同变化原因和明确消费者时，在最近共同边界抽取。
5. 以上均不成立才新增实现；说明差异与归属即可，不要求为小改动写独立设计报告。

判断复用必须比较权限、租户、金额单位、日期区间、状态语义、错误处理和副作用。
看起来相同但由不同规则驱动的代码可以保持独立；不要用大量布尔参数兼容互斥用例。

抽取共享能力时：

- 最小可用接口、明确输入输出与副作用，不泄露 DAL 实体、HTTP 细节或 UI 状态。
- 跨前后端契约调整时列明请求、响应、错误及消费者；字段新增/删除、可空性、
  大整数 ID、日期格式和金额单位都属于契约，不靠两端类型检查推定一致。
- 优先功能内私有模块；只有跨功能实际使用时才上移到应用公共层。
- 同一领域规则由一个服务/策略拥有；批处理、人工重试、定时任务与页面操作复用它。
- 通用层不导入业务页面；业务模块经明确的公开入口协作，不依赖另一模块内部文件。
- 修改共享函数、组件、请求拦截器或缓存时，查调用方并验证所有受影响语义；
  不能以当前页面通过作为共享改动的全部证据。
- 不为复用跨应用相对路径引用 `../camera-rental-*/src/**`。
  引入共享包前明确至少两个实际消费者、平台限制、依赖方向与测试/版本责任；
  有实质架构影响时先说明方案。不同框架页面不强行统一为同一组件。

## 2. 后端职责与依赖

保留 Spring Boot 模块化单体和芋道现有结构，不新增平行架构。
租赁模块的 `api` 提供跨模块契约，`biz` 实现业务；不能让 API 模块反向依赖 Biz。

| 层 | 应承担 | 不应承担 |
| --- | --- | --- |
| Controller / Request、Response VO | 协议适配、入口校验、权限声明、统一响应 | Mapper 调用、排期/结算规则、第三方 HTTP |
| Service / 用例编排 | 业务规则、事务、幂等、状态转换、多能力协作 | 拼签名、任意跨模块直改数据表、面向页面的显示格式 |
| Policy / 领域计算 | 可独立测试的规则判定和精确计算 | 隐藏 IO、写数据库、依赖请求上下文 |
| DAL / Mapper / DO | 数据查询、持久化、锁与约束配合 | UI DTO、跨领域流程编排 |
| Convert / Mapper 转换 | VO/DTO/DO 的显式边界映射 | 决定授权、订单状态、价格或履约流程 |
| Integration Client / Adapter | 外部协议、签名、序列化、超时、错误转换 | 决定内部订单能否发货或退款 |
| Job / Webhook | 调度、接收、验签、去重、调用服务 | 复制 Service 业务规则 |

这些是职责边界，不要求每个简单 CRUD 都新增 Policy、接口和实现两套文件。
沿用附近明确的 Service/ServiceImpl 约定；新增注入代码优先使用构造器与显式依赖，
不为统一注入风格改写无关类。

跨模块优先使用已公开的 API/Service。ERP 管采购与数量库存，租赁管设备实例与履约；
遵循现有桥接，不能为读取方便引入循环依赖、越权 Mapper 或跨模块共享可变实体。
状态改变应通过负责该状态的服务入口，先验证转换前置条件，再原子更新相关记录。

### 一致性与失败边界

- 订单、分配、排期等不变量在同一业务事务中维护；注意 Spring 代理、自调用导致的
  事务失效以及捕获异常后的错误提交。不得通过吞异常返回成功。
- 并发操作先明确锁对象和顺序、幂等键作用域、唯一约束与冲突响应。
  排期空窗口并发不能仅锁查询结果，同设备占用写入复用现有设备锁入口。
- 数据库事务不能回滚第三方发货/支付。发生外部调用时明确请求幂等、超时后的状态查询、
  本地结果记录、失败补偿/人工复核，不能无条件重试写操作。
- 事务内避免长耗时网络调用；调整为异步时必须保证已提交数据才能被消费，
  需要可靠投递才采用现有持久化任务/outbox 等机制，不默认新增消息中间件。
- 缓存不作为库存或权限的唯一依据。写操作明确失效时机，租户切换不得复用上一租户数据。
- 查询先用有界分页/批量获取解决 N+1；索引和聚合优化以查询条件与测量为依据，
  不把分页换成全量拉取或用前端内存替代服务端查询。

## 3. 前端职责与状态

概念上的依赖方向为：页面/路由编排 → 功能组件与 hook/composable → API 与纯模型。
共享 UI 和通用工具不反向依赖页面。实际目录沿用各应用 AGENTS 的入口，不为统一名字搬文件。

- 页面组织用例和布局；可复用交互放组件，状态/副作用放 hook 或 composable，
  请求与 DTO 放 API 层，纯转换/展示计算放模型或工具。避免大页面混合所有职责。
- 使用现有请求封装处理认证、租户、刷新令牌、错误和取消；组件不重复创建 HTTP 客户端。
  外部 DTO 在边界归一化；不要通过 `as` 断言掩盖响应差异。
- 本地输入/弹窗状态留在局部；跨页面会话、偏好等按实际共享范围放 store/context。
  服务器数据保持单一来源，派生值用计算值；不维护可由已有状态推导的多份可变副本。
- Vue 使用单向 props/emits，避免修改 props；React render 保持纯净，不直接修改 state。
  watcher/effect 明确依赖及清理，避免链式相互触发。
- 查询条件变化处理并发响应覆盖；轮询、事件监听、订阅、定时器卸载时释放。
  提交处理重复点击和失败恢复；前端禁用按钮不能代替后端幂等。
- 保留当前组件库和设计 token。先复用项目组件，再组合当前库能力；
  不新增第二套 UI 框架，不用全局 CSS 覆盖解决单页面问题。
- 路由、认证、缓存键、iframe/postMessage 集成须核对现有协议；消息校验 origin、source
  和 payload，不能为免登绕过权限或扩大信任域。
- 不把业务订单状态硬编码为按钮是否可用的另一套真相；按后端状态/能力与权限展示，
  并正确处理服务端拒绝、状态已变更和重新加载。

### 界面的渐进式披露

- 首屏优先展示当前任务的关键状态、必要字段和主操作；高级筛选、审计、历史与
  低频配置通过清晰命名的折叠区、详情、抽屉或下一步按需展开。
- 不隐藏完成任务必需的字段、权限拒绝原因、表单错误、费用、排期冲突或不可逆影响。
  折叠不能导致用户找不到错误，应自动展开或提供可定位提示。
- 同一流程复用相同标签、状态颜色、金额/日期格式；明确区分计租与设备占用。
  内部技术名、测试阶段和实现细节不进入普通业务操作文案。
- 处理加载、空数据、失败重试、无权限、局部刷新及提交结果；加载不能伪装成空列表。
- 弹窗/抽屉支持键盘与焦点返回；表单有标签，错误可读，窄屏不遮挡主要操作。
  增加披露层级应减少用户判断成本，不以多弹窗制造额外步骤。

## 4. 代码规范

- 以目标应用的 EditorConfig、ESLint、Prettier、TypeScript/POM 和附近代码为准。
  先看脚本是否包含 `--fix`/`--write`；只格式化本次修改，不顺带升级格式规则。
- 名称表达领域语义和单位，例如金额分、`endExclusive`、预计日期与实际时间明确区分。
  新增状态/错误码复用现有枚举与常量；外部标识和内部主键不得混用。
- 函数保持单一职责，优先守卫语句降低嵌套；按职责/变化原因拆分，
  不以机械的行数阈值拆出大量转发函数。注释解释约束与原因，不复述代码。
- TypeScript 避免无理由 `any`、非空断言与双重断言；不可信输入用 `unknown` 加验证。
  Java 避免 raw type、字符串拼 SQL、以 null 隐式表示多种失败。
  既有 JavaScript 应用沿用其类型辅助和校验，不借小改动强制迁移全项目到 TS。
- 参数校验分两层：边界检查形状/格式，Service 检查业务不变量、权限和状态。
  禁止宽泛复制属性写入受保护字段；Patch 的未提供/null/空值语义必须明确。
- 纯计算和 IO 分离，避免导入即执行副作用、隐藏全局可变状态和不可控当前时间。
  测试时间相关业务时使用现有可控时钟/时间参数，不为一处使用引入全局容器。
- 对错误进行明确分类并保留安全诊断信息；不空 catch、不吞 Promise rejection、
  不把未知外部值默认为“成功/可租/已支付”。日志不得包含凭据或客户隐私。
- 删除因本次修改失效的代码、导入与分支；不添加未使用的扩展点、备用方案、
  魔法兜底或永久兼容别名。无关历史问题作为后续发现报告。

## 5. 设计模式的选择与反例

先描述实际问题、变化轴和最简单替代方案，再决定是否引入模式。
选择应能说明它减少了哪类重复或耦合，以及增加了什么维护成本。

| 模式/做法 | 适用条件 | 使用边界 |
| --- | --- | --- |
| 组合、hook/composable | 多处共享同一状态过程或交互 | 不把无关业务塞进万能 hook，不泄露页面状态到公共层 |
| Strategy / Policy | 已存在可独立变化的规则，输入输出语义稳定 | 简单固定分支可直接表达，不为每个 if 建类 |
| Adapter / 边界映射 | 外部协议或平台 DTO 与内部语义不同 | 外部字段止于集成/API 层，不让业务 Service 理解签名 |
| Facade / 用例编排 | 多入口共享同一完整业务过程 | 委托领域服务，不形成包含所有规则的巨大 Service |
| 显式状态转换 | 多状态、多触发入口且必须保护不变量 | 先复用枚举、转换方法和守卫；不默认引入状态机框架 |
| Factory | 有真实的多实现构造/选择需求 | Spring 注入或简单构造已足够时不新增工厂层 |
| 事件 / 持久化任务 | 提交后副作用、长任务或需可靠重试 | 明确事务、投递、顺序、幂等与重放；不用内存事件保证核心一致性 |

现有 Mapper 已覆盖持久化边界时，不为形式增加一层空 Repository。
没有实质多态关系时不建立深继承/Template Method；没有独立读写负载需求时
不新增 CQRS、事件溯源或微服务。复杂新边界记录在 `docs/decisions/`，
包括问题、选项、选择、代价和迁移影响；普通组合与局部抽取无需 ADR。
